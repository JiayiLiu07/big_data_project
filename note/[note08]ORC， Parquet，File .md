# 数据存储格式:ORC、Parquet 和普通的文件格式（如 CSV、JSON 等）

## -----↓优化版↓-----
## CSV (Comma-Separated Values)

### 为什么会出现：
-   一种**古老**的文件格式，计算机诞生初期即存在。
-   目标：以**简单、通用**的方式存储和交换**表格数据**。

### 它用来解决什么问题：
-   `数据交换`：方便在不同系统和应用程序间交换表格数据。
-   `小数据集处理`：适合**快速读写**小规模数据集。

### 它本身又遇到了什么问题：
-   `无法存储复杂数据结构`：仅限简单表格，不支持层级或键值对。
-   `处理特殊字符困难`：如逗号本身，需额外转义。
-   `不支持数据类型`：不保存类型信息，需手动指定。
-   `不适合大规模数据`：**行导向**导致查询慢，文件体积相对较大。

## JSON (JavaScript Object Notation)

### 为什么会出现：
-   满足**互联网时代数据交换**的需求。
-   Web 应用需要**轻量级、易于人读写、易于机器解析和生成**的格式。--> JSON基于文本，易于阅读和编写，同时也易于机器解析和生成

### 它用来解决什么问题：
-   `数据交换`：方便交换数据对象，**支持复杂数据结构**（嵌套键值对、数组）。
-   `灵活性`：易于增删字段，适合动态数据结构。

### 它本身又遇到了什么问题：
-   `读取速度慢`：**行导向**，查询需逐行读取，不适合大规模数据快速查询。
-   `文件体积大`：结构相对冗长，通常比 CSV 和 Parquet 大。
-   `不支持模式验证`：无法验证模式，可能导致数据不一致。

## Parquet

### 为什么会出现：
-   大数据技术发展，传统**行导向格式 (CSV, JSON) 遇性能瓶颈**。
-   目标：**提高大规模数据处理效率，降低存储成本**。

### 它用来解决什么问题：
-   `提高查询效率`：采用**列存储**，快速读取特定列，**显著减少数据扫描范围**。
-   `压缩和存储优化`：支持**高效压缩**和多种编码，减小体积，优化读写。
-   `支持复杂数据结构`：可存储**嵌套数据结构**。

### 它本身又遇到了什么问题：
-   `需要专门知识`：无法用普通文本编辑器打开，需特定工具/语言（如 `Apache Spark`, `Apache Hadoop`）。
-   `社区支持有限`：主要在 `Apache Spark` 和 `Apache Hadoop` 生态中，外部支持较少。

## ORC (Optimized Row Columnar)

### 为什么会出现：
-   进一步优化大数据处理中的**写入性能**和**事务支持**。

### 它用来解决什么问题：
-   `写入性能优化`：适合**写入密集型任务**，高效处理大规模数据写入。
-   `支持ACID事务`：支持 `Apache Hive` 的 **ACID 事务**（更新、删除、合并）。
    - ORC 格式内部设计了对事务的支持机制：
        - 增量文件 (Delta Files)： 当数据发生更改时，Hive 不会直接修改原始的 ORC 文件。相反，它会在表的目录下创建特殊的“增量文件”（delta files），这些文件记录了插入、更新或删除的变更事件。
        - 读时合并 (Read-Time Merge)： 当查询数据时，Hive 引擎会读取基准数据文件，并根据这些增量文件实时地应用更改，从而呈现出最新的、一致的数据视图。
        - 压缩 (Compaction)： 为了防止增量文件过多导致查询性能下降（每次查询都需要合并大量小文件），Hive 会有后台进程定期将这些增量文件与基准数据文件合并，生成新的、更紧凑的 ORC 文件。
    - **ACID 是数据库事务管理中的一组属性**，旨在保证数据库事务的可靠性和数据的完整性。
        - A - Atomicity (原子性)-->要么都做，要么都不做
        - C - Consistency (一致性)-->数据规则不能坏
        - I - Isolation (隔离性)-->多个事务互不干扰
        - D - Durability (持久性)-->一旦提交，数据就丢不了
-   `性能优越`：大规模数据处理时，提供高效读写性能。

### 它本身又遇到了什么问题：
-   `社区支持较弱`：相较 Parquet，社区支持更弱。
    - 社区支持指的是：围绕一个技术、软件或项目（比如这里的 ORC 或 Parquet 文件格式）的开发者、用户和贡献者群体所提供的帮助、资源和活跃度。
    - 社区支持弱 也就说明：遇到问题时，更难快速找到现成的解决方案/相关的学习资源（比如：博客）可能不如 Parquet 丰富或更新及时。/在某些特定编程语言或工具中，对 ORC 的支持可能不如 Parquet 成熟或全面。/围绕 ORC 的开发者和活跃用户群体相对较小，讨论和贡献的活跃度可能较低。
-   `适用场景有限`：主要用于 `Apache Hive` 和 `Hadoop` 生态，其他平台支持少。

### 1. ORC 文件格式

- **ORC 的做法** ：它会把书里的信息重新整理一下，把所有人的年龄都放在一个地方，所有人的名字放在另一个地方，所有人的地址放在第三个地方。这样，你要是想算平均年龄，就直接去那个专门放年龄的地方看就行，不用再一页一页翻了。

- **优点** ：找数据特别快，尤其是当你只需要看某些特定的信息（比如年龄、收入）的时候。而且，它还会把数据压缩一下，让书变得更薄，节省空间。

- **缺点** ：这种格式比较复杂，不是所有工具都能直接读取，主要用在大数据分析的场景里。

### 2. Parquet 文件格式

- **Parquet 的做法** ：它就像一个标准化的乐高积木套装，把所有的积木都设计成统一的形状和接口。这样，不管你用什么工具（比如不同的大数据处理软件），都可以很方便地拼起来。

- **优点** ：它和 ORC 有点像，也是把数据按列存储，找数据很快，还能压缩数据。但它还有一个特别厉害的地方——它被设计成一种“通用格式”，几乎所有的大数据工具都能用它，就像乐高积木一样，到处都能用。

- **缺点** ：和 ORC 一样，它也比较复杂，不适合简单的场景。

### 3. CSV 文件格式

- **CSV 的做法** ：它就像是一张简单的纸表格，用逗号（或者别的符号）把每一列的信息分开。比如，John,25,New York，这就是一行数据。

- **优点** ：非常简单，所有人都能看懂，用普通的文本编辑器就能打开。几乎所有的工具都能处理这种格式，就像纸表格一样通用。

- **缺点** ：因为它太简单了，没有压缩，也没有优化，所以找数据的时候比较慢，尤其是数据量很大的时候。

### 4. JSON 文件格式

- **JSON 的做法** ：它把信息组织成这种“卡片故事”的形式，每个信息都有一个名字（比如“名字”“年龄”“地址”），然后用大括号 {} 把它们包起来。比如：{ "name": "John", "age": 25, "address": "New York" }。

- **优点** ：这种格式很灵活，可以表示很复杂的信息（比如嵌套的故事），而且很容易读，人类看起来很舒服。

- **缺点** ：它也没有压缩，数据量大的时候会比较占空间，而且找数据的时候没有 ORC 和 Parquet 那么快。

### 对比 ORC 和 Parquet
- **共同之处**：
    - 都是`列式存储`；
    - 都支持`数据压缩`；
    - 都支持`复杂数据类型`
- **不同之处**：orc自带索引 parquet没有自带索引

- **总结**： 
1. ORC：就像一个“高效但专一”的收纳盒，读取速度快，存储效率高，但`主要用在 Hadoop 生态系统里`。
2. Parquet：就像一个“灵活且通用”的收纳盒，写入速度快，兼容性好，`适合各种大数据工具`。




| 特性 | ORC | Parquet | CSV | JSON | 
| --- | --- | --- | --- | --- | 
| 存储方式 | 列式存储 | 列式存储 | 行式存储 | 嵌套结构 | 
| 压缩支持 | 支持多种压缩算法 | 支持多种压缩算法 | 一般不压缩 | 一般不压缩 | 
| 编码技术 | 字典编码、RLE 等 | 字典编码、Delta 编码等 | 无 | 无 | 
| 数据类型支持 | 支持复杂数据类型 | 支持复杂数据类型 | 无数据类型信息 | 支持复杂嵌套数据类型 | 
| 兼容性 | 主要用于 Hadoop 生态系统 | 跨平台兼容 | 通用性强 | 通用性强 | 
| 适用场景 | 数据仓库分析 | 数据交换、数据湖 | 数据导入导出 | Web 数据交换、复杂嵌套数据存储 |
